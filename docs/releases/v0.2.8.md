# myopenclaw v0.2.8

补丁版本（2026-11-16）。这一版把**钉钉 CLI（`dws`）作为 Hermes 的一项能力**接进来，
并且**只给默认 profile（爱玛士 / `hermes` 容器）**。其余三个 profile 拿到二进制但
没有 token 目录、也调不通；OpenClaw 三栈与 Claude Code 未改动。**必须重建 hermes 镜像**。

## 本版变更

### 钉钉 Workspace CLI（`dws`）：只有爱玛士能用

钉钉官方 CLI 覆盖 17 个产品域：AI 表格、日历、通讯录、群聊与机器人、待办、OA 审批、
考勤、日志（日报周报）、钉钉文档、云盘、AI 听记、邮箱、在线电子表格、知识库、DING 等。

- **镜像**：`npm install -g dingtalk-workspace-cli@1.0.26`。该 npm 包内自带
  darwin/linux/win 五平台预编译 Go 二进制，postinstall 只解压，**不需要**额外下载
  平台包；构建期补装 `unzip`（postinstall 解 `dws-skills.zip` 的硬依赖）后即卸。
  `HOME` 指到 `/tmp`，避免 postinstall 把官方 skill 复制进 `/root/.hermes/skills`。
- **skill**：官方 skill 原样落仓库 `skills/dws/`（39 个文件，含 17 个产品参考与
  批量脚本），由 `scripts/start.sh` 链进 `~/.hermes/skills/dws`（默认 profile）。
- **隔离**：宿主机 `~/.dws-cli` 只挂给 `hermes` 为 `/opt/dws-config`，并且只有它设
  `DWS_CONFIG_DIR` / `DWS_KEYCHAIN_DIR`。四个 hermes 容器共享 `/opt/data`，所以
  token 绝不能落在 `$HOME/.dws` 或 `$HOME/.local/share/dws-cli`。

### 踩到并固化的坑：token 的真正落点是 `DWS_KEYCHAIN_DIR`

`dws` 把凭据写进 `$DWS_KEYCHAIN_DIR/dws-cli/{auth-token.enc,dek}`，**默认路径是
`$HOME/.local/share/dws-cli`**（容器里 = `/root`，重建即丢）；`DWS_CONFIG_DIR`
只管 `app.json` / `identity.json` / `logs` / 工具缓存。第一次只设前者时症状是
「`dws auth login` 成功 → `docker compose up -d` → 又变未登录」。两个变量都钉在
挂载卷上之后，容器重建、镜像升级都不掉登录态（真机验证过一轮重建）。

### 共享数据卷卫生：`dws-off` bundle

隔离验证时在 `/opt/data`（= `~/.hermes`，四容器共享**且每天进云备份**）里发现
`dws` 残留：`.dws/cache/…`（1.5MB）与 `.local/share/dws-cli/dek`。成因是另外三个
profile 的 `$HOME=/opt/data`，随手跑一次 `dws` 就写进去了。

- 新增 base bundle `dws-off`：把 `DWS_CONFIG_DIR`/`DWS_KEYCHAIN_DIR` 钉到容器内
  `/tmp/dws/*`，coder / 道元 / finance 各自挂上；即使有人误跑 `dws auth login`，
  token 也只活在该容器内，不跨 profile、不进云备份。
- 残留已清理；守卫 `tests/test_dws_cli_wiring.py::TestSharedVolumeHygiene` 防回退。

### 测试与文档

- 新增 `tests/test_dws_cli_wiring.py`（15 项）：Dockerfile pin 存在且**满足 skill
  自己声明的 `cli_version` 下限**、只有默认 profile 挂 `~/.dws-cli` + skill 且设两个
  目录变量、其余三个 profile 的目录变量只能是 `/tmp/*`、skill 不得链进它们、
  `dws-off` bundle 必须存在且被挂上、文档与 mkdocs 引用。
- `tests/test_render_agents.py` 的 bundle 顺序清单同步（新增 bundle 必须显式登记）。
- 新增 `docs/dingtalk-cli.md`（授权流程、隔离设计、验证命令、已知噪音、升级流程）
  并加入 mkdocs nav 与 `CLAUDE.md`。

## 升级注意

1. **重建镜像 + 四个容器**（二进制在镜像里）：
   ```bash
   docker compose build hermes
   docker compose up -d hermes hermes-coder hermes-finance hermes-daoyuan
   ```
2. **首次授权（一次性，设备流）**——这是**用户身份** OAuth，不是 bot 身份，不能靠
   `.env` 里的 AppKey 免登录：
   ```bash
   docker compose exec -u hermes -it hermes dws auth login --device
   ```
   屏幕给出 `user_code` + 链接，授权完成后 `dws auth status` 应为 `authenticated: true`。
   **宿主机不需要装 `dws`**（本机安装不是必需路径）。
3. **`start.sh` 会自动建 `~/.dws-cli` 并链 skill**；不跑 `start.sh` 而是手工 `up -d`
   时，宿主机目录不存在会被 Docker 以 root 建出来，容器内可能写不进 token。
4. **token 不进云备份**：`hermes/scripts/backup.sh` 只备 `~/.hermes`，`~/.dws-cli`
   刻意不覆盖（个人钉钉 token 不上云盘）。换机/丢目录 → 重跑一次设备流。
5. **回滚**：回退镜像即可，`~/.dws-cli` 留在宿主机不影响任何其他能力。

## 已知边界

- **`conference` 插件噪音**：每次调用都会打一行
  `WARN plugin: stdio initialize failed plugin=conference` —— 钉钉会议能力要本机
  钉钉桌面客户端（≥ 8.3.20）在线，容器里必然没有。只影响会议，其余产品照常。
- **能力边界由钉钉管理员决定**：本版只保证 CLI 可用与认证链路；具体产品（如
  AI 表格、审批写操作）能否调通取决于后台开通的 scope，报错以 `dws` 返回为准。
- **所有操作都以你个人身份执行**：token 是用户身份 token，读写群消息、文档、
  审批与以你名义发消息都走同一身份。危险操作（删表/删记录/撤回/拒绝审批）在 skill
  里要求先确认再 `--yes`。
- **落盘加密是「防误读」而非「防本机读取」**：`auth-token.enc` 是密文，但 `dek`
  就在同一目录（目录 700、只挂给 hermes、不进云备份）。容器内 agent 以 root 运行，
  拿到 token 是「能干活」的必然结果。
- **`dws` 会按服务发现动态调整参数**：`--help` / `dws schema` 是事实源，仓库里的
  `skills/dws/references/` 视为参考；升级 CLI 时先改 Dockerfile pin，再用同版本覆盖
  `skills/dws`，最后跑 `pytest tests/test_dws_cli_wiring.py`。
- **设备流需要人工**：不要把 `dws auth login` 塞进 cron；refresh token 30 天未用即失效。
